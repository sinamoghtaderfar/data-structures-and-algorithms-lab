# بنچمارک Binary Search

[English](./BENCHMARK.md)

در این آزمایش، عملکرد **Linear Search** و **Binary Search** را به‌صورت عملی با یکدیگر مقایسه کردم.

هدف فقط تکرار پیچیدگی‌هایی که از نظر تئوری می‌دانیم نبود:

```text
Linear Search  -> O(n)
Binary Search  -> O(log n)
```

می‌خواستم ببینم این تفاوت وقتی الگوریتم‌ها واقعاً اجرا می‌شوند چگونه خودش را نشان می‌دهد.

برای همین دو چیز را اندازه‌گیری کردم:

1. تعداد مقایسه‌هایی که هر الگوریتم انجام می‌دهد؛
2. زمان واقعی اجرای هر الگوریتم.

---

## سناریوی آزمایش

برای هر اندازه‌ی ورودی، داده‌ها به شکل زیر ساخته می‌شوند:

```python
array = range(size)
```

و target را برابر خود `size` قرار می‌دهیم:

```python
target = size
```

از آنجایی که `range(size)` شامل اعداد `0` تا `size - 1` است، target داخل داده‌ها وجود ندارد.

مثلاً:

```python
array = range(1000)
target = 1000
```

در این حالت، جست‌وجو ناموفق خواهد بود.

این انتخاب عمدی است، چون می‌خواهیم یک **حالت worst case** مناسب برای مقایسه داشته باشیم.

Linear Search مجبور است تمام عناصر را بررسی کند تا در نهایت بفهمد target وجود ندارد.

اما Binary Search در هر مرحله تقریباً نصف محدوده‌ی باقی‌مانده را حذف می‌کند.

---

## چرا از `range()` استفاده کردم؟

در نسخه‌ی اولیه‌ی آزمایش از این استفاده کرده بودم:

```python
list(range(size))
```

برای ورودی‌های کوچک مشکلی نداشت، اما وقتی تعداد عناصر خیلی زیاد شد، مصرف RAM به‌شدت بالا رفت.

ساختن ده‌ها یا صدها میلیون عدد Python می‌تواند چندین گیگابایت حافظه مصرف کند.

در این Benchmark نیازی نداریم تمام این اعداد واقعاً داخل حافظه ساخته شوند.

`range()` امکانات موردنیاز ما را دارد:

```python
len(array)
array[index]
iteration
```

و در عین حال حافظه‌ی بسیار کمتری مصرف می‌کند.

به همین دلیل:

```python
range(size)
```

برای این آزمایش انتخاب مناسب‌تری بود.

---

## شمارش تعداد مقایسه‌ها

در قسمت اول Benchmark اصلاً زمان اجرا مهم نیست.

فقط می‌شماریم هر الگوریتم چند بار یک مقدار را بررسی می‌کند.

یک اجرای نمونه تقریباً چنین نتیجه‌ای داشت:

| اندازه ورودی | Linear Search | Binary Search |
| -----------: | ------------: | ------------: |
|        1,000 |         1,000 |            10 |
|       10,000 |        10,000 |            14 |
|      100,000 |       100,000 |            17 |
|      500,000 |       500,000 |            19 |

تفاوت خیلی سریع بزرگ می‌شود.

در Linear Search با افزایش اندازه‌ی ورودی، تعداد مقایسه‌ها نیز تقریباً به همان نسبت افزایش پیدا می‌کند.

اما در Binary Search، حتی بزرگ شدن شدید ورودی فقط چند مرحله به جست‌وجو اضافه می‌کند.

مثلاً:

```text
1,000 عنصر
Binary Search -> 10 مقایسه

500,000 عنصر
Binary Search -> 19 مقایسه
```

یعنی اندازه‌ی ورودی **500 برابر** شده، اما Binary Search فقط به 9 مقایسه‌ی بیشتر نیاز داشته است.

این همان رفتاری است که پشت:

```text
O(log n)
```

قرار دارد.

### نمودار تعداد مقایسه‌ها

![مقایسه تعداد عملیات Linear Search و Binary Search](./assets/benchmark_comparisons.png)

برای هر دو محور از مقیاس لگاریتمی استفاده شده است.

دلیلش این است که اختلاف بین دو الگوریتم بسیار زیاد است و با نمودار عادی، خط Binary Search تقریباً به کف نمودار می‌چسبد.

در این نمودار رشد Linear Search تقریباً همراه با اندازه‌ی ورودی است، در حالی که Binary Search بسیار آهسته‌تر رشد می‌کند.

## اندازه‌گیری زمان واقعی اجرا

شمارش comparisonها رفتار الگوریتم را مستقیم‌تر نشان می‌دهد.

اما می‌خواستم ببینم در اجرای واقعی Python چه اتفاقی می‌افتد.

برای اندازه‌گیری زمان از:

```python
time.perf_counter_ns()
```

استفاده کردم.

این timer برای اندازه‌گیری زمان‌های کوتاه مناسب است و نتیجه را با دقت nanosecond ارائه می‌کند.

اما خیلی زود به یک مشکل دیگر رسیدم.

Binary Search در این آزمایش ممکن است فقط چند microsecond طول بکشد.

وقتی فقط یک بار چنین تابع سریعی را اندازه می‌گرفتم، نتایج بالا و پایین می‌شدند.

مثلاً ممکن بود یک اجرا:

```text
2 µs
```

و اجرای دیگری بدون تغییر مهمی:

```text
8 µs
```

باشد.

این لزوماً به معنی تغییر عملکرد الگوریتم نیست.

عوامل دیگری هم روی چنین زمان کوتاهی اثر می‌گذارند، مثل:

* زمان‌بندی سیستم‌عامل؛
* overhead خود Python؛
* وضعیت CPU؛
* برنامه‌های دیگری که همزمان اجرا می‌شوند؛
* noise مربوط به اندازه‌گیری.

پس فقط گذاشتن یک timer قبل و بعد از تابع کافی نبود.

## Warm-Up

قبل از شروع اندازه‌گیری اصلی، تابع یک بار اجرا می‌شود ولی زمان آن ثبت نمی‌شود:

```python
func(array, target)
```

این همان warm-up است.

هدف این است که اجرای اول تأثیر زیادی روی نتیجه‌ی نهایی نداشته باشد.

Warm-up تمام noise سیستم را حذف نمی‌کند، ولی باعث می‌شود اندازه‌گیری کمی پایدارتر باشد.

---

## Calibration خودکار

مشکل مهم‌تر این بود که اجرای یک Binary Search برای اندازه‌گیری دقیق بیش از حد کوتاه است.

می‌توانستم به‌صورت دستی بگویم:

```text
Binary Search را 1000 بار اجرا کن.
```

اما این عدد کاملاً دلخواه بود.

به‌جای آن، Benchmark خودش تعداد اجرای مناسب را پیدا می‌کند.

از:

```text
1
```

شروع می‌کند و تعداد اجراها را هر بار دو برابر می‌کند:

```text
1
2
4
8
16
32
64
...
```

تا زمانی که مدت کل اندازه‌گیری حداقل حدود:

```text
50 ms
```

شود.

در نتیجه اگر تابع کند باشد، تعداد اجرای زیادی لازم نیست.

اما اگر تابع بسیار سریع باشد، ممکن است هزاران بار اجرا شود.

به این ترتیب تعداد iterationها بر اساس سرعت واقعی تابع تنظیم می‌شود.

---

## محاسبه‌ی زمان یک Search

بعد از Calibration، الگوریتم چندین بار داخل یک بازه‌ی اندازه‌گیری اجرا می‌شود.

به‌صورت مفهومی:

```text
شروع timer

اجرای Search به تعداد N بار

توقف timer
```

بعد:

```text
زمان یک اجرا =
زمان کل / تعداد اجراها
```

محاسبه می‌شود.

این روش برای تابعی که فقط چند microsecond طول می‌کشد، قابل‌اعتمادتر از اندازه‌گیری یک اجرای منفرد است.

## تکرار اندازه‌گیری و Median

هر measurement چند بار تکرار می‌شود.

در حال حاضر:

```python
repeat = 7
```

است.

در نهایت به‌جای اینکه فقط یک نتیجه را قبول کنیم، median زمان‌ها را می‌گیریم:

```python
statistics.median(times)
```

این کار باعث می‌شود اگر یکی از اجراها به دلیل سیستم‌عامل یا یک process دیگر ناگهان کندتر شد، تأثیر کمتری روی نتیجه‌ی نهایی داشته باشد.

## نتایج Runtime

اعداد دقیق در هر اجرا ممکن است کمی متفاوت باشند و روی سیستم‌های مختلف هم یکسان نخواهند بود.

در اجرای این Benchmark نتایجی تقریباً در این محدوده دیده شد:

| اندازه ورودی |    Linear Search | Binary Search |
| -----------: | ---------------: | ------------: |
|        1,000 |    حدود 50–60 µs |     حدود 2 µs |
|       10,000 | حدود 500–1000 µs |   حدود 2–3 µs |
|      100,000 |    حدود 5,000 µs |     حدود 3 µs |
|      500,000 |         ده‌ها ms |   حدود 3–4 µs |

عدد دقیق مهم‌ترین بخش این آزمایش نیست.

چیزی که اهمیت دارد **نحوه‌ی رشد زمان با افزایش ورودی** است.

Linear Search با بزرگ شدن داده‌ها به‌وضوح پرهزینه‌تر می‌شود.

در مقابل، زمان Binary Search بسیار آهسته‌تر افزایش پیدا می‌کند.

![مقایسه Runtime در Linear Search و Binary Search](./assets/benchmark_runtime.png)

برای این نمودار هم هر دو محور logarithmic هستند.

این کار اجازه می‌دهد زمان‌هایی که چندین مرتبه بزرگی با یکدیگر اختلاف دارند، روی یک نمودار قابل مشاهده باشند.

## تفاوت Runtime و Big O

این دو نمودار دقیقاً یک چیز را اندازه نمی‌گیرند.

نمودار comparisonها رفتار خود الگوریتم را مستقیم‌تر نمایش می‌دهد:

```text
Linear Search  -> O(n)
Binary Search  -> O(log n)
```

اما Runtime یک اندازه‌گیری تجربی است.

زمان واقعی اجرا به عوامل زیادی وابسته است:

```text
CPU
نسخه Python
سیستم‌عامل
بار سیستم
Python interpreter
```

بنابراین اگر Benchmark امروز مثلاً:

```text
2.5 µs
```

برای Binary Search نشان دهد، معنی آن این نیست که Binary Search همیشه و روی همه‌ی سیستم‌ها دقیقاً همین مقدار زمان می‌برد.

چیزی که باید از نمودار برداشت کنیم **روند رشد** است، نه یک عدد ثابت.

## چرا زمان Sorting را حساب نکردم؟

Binary Search نیاز دارد داده‌ها از قبل مرتب باشند.

در این Benchmark فرض می‌کنیم collection از قبل sorted است.

بنابراین زمان sorting وارد اندازه‌گیری نشده است.

سؤالی که این آزمایش پاسخ می‌دهد این است:

> اگر یک collection مرتب داشته باشیم، عملکرد Linear Search و Binary Search برای lookup چه تفاوتی دارد؟

اما سؤال دیگری مثل:

> اگر داده‌ها مرتب نباشند، آیا ابتدا sort کردن و بعد استفاده از Binary Search ارزش دارد؟

یک آزمایش جداگانه می‌خواهد.

پاسخ آن به تعداد searchهایی که قرار است انجام شوند و شرایط برنامه بستگی دارد.

## چیزی که از این آزمایش یاد گرفتم

تا قبل از این Benchmark، تفاوت:

```text
O(n)
```

و:

```text
O(log n)
```

از نظر تئوری مشخص بود.

اما دیدن اعداد واقعی باعث شد تفاوت خیلی ملموس‌تر شود.

Binary Search از:

```text
10
14
17
19
```

comparison عبور می‌کرد، در حالی که Linear Search به:

```text
1,000
10,000
100,000
500,000
```

رسیده بود.

قسمت جالب‌تر برای من این بود که خود Benchmark کردن هم مسئله‌ی جداگانه‌ای است.

در ابتدا تصور ساده این بود:

```text
timer start
algorithm
timer end
```

اما برای الگوریتمی که چند microsecond طول می‌کشد، این روش چندان قابل اعتماد نیست.

در این آزمایش با مفاهیم دیگری هم درگیر شدم:

* ساخت worst-case مناسب؛
* تأثیر مصرف حافظه روی آزمایش؛
* استفاده از high-resolution timer؛
* runtime noise؛
* warm-up؛
* repeated measurements؛
* median؛
* calibration خودکار؛
* logarithmic scale برای visualization.

خود Binary Search الگوریتم نسبتاً ساده‌ای بود.

اما تلاش برای **اندازه‌گیری درست عملکرد آن** بخش متفاوت و مفیدی از این تمرین بود.
