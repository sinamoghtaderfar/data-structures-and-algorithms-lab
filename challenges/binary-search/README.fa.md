# چالش Binary Search — جست‌وجوی مرزی در لاگ‌های سرور

در این چالش Binary Search را یک قدم فراتر از پیدا کردن یک مقدار دقیق می‌بریم و از آن برای یک مسئله‌ی واقعی‌تر استفاده می‌کنیم:

**پیدا کردن اولین لاگ سرور که زمان آن برابر یا بعد از زمان موردنظر باشد.**

ایده‌ی اصلی مسئله این است:

> در میان timestampهای مرتب‌شده، اولین موقعیتی را پیدا کنیم که مقدار آن بزرگ‌تر یا مساوی target باشد.

این مسئله نمونه‌ای از **Boundary Search** یا جست‌وجوی مرزی با استفاده از Binary Search است.

---

## مسئله

فرض کنیم یک سرور لاگ‌های خود را به ترتیب زمانی ذخیره می‌کند.

هر لاگ شامل دو بخش است:

```text
(timestamp, message)
```

مثلاً:

```python
logs = [
    ("10:00:01", "Server started"),
    ("10:02:15", "User login"),
    ("10:05:40", "Payment request"),
    ("10:08:12", "Database warning"),
    ("10:08:48", "Server warning"),
    ("10:12:33", "User logout"),
]
```

تابع زیر را پیاده‌سازی می‌کنیم:

```python
find_first_log_at_or_after(logs, target_time)
```

وظیفه‌ی تابع این است که index **اولین لاگی** را برگرداند که timestamp آن برابر یا بعد از `target_time` باشد.

یعنی دنبال اولین indexای هستیم که شرط زیر را برقرار کند:

```text
timestamp >= target_time
```

اگر هیچ لاگ معتبری وجود نداشت، باید:

```python
None
```

برگردانده شود.

راه‌حل باید با استفاده از **Binary Search** نوشته شود.

---

## چرا Binary Search؟

ساده‌ترین راه این است که لاگ‌ها را از ابتدا یکی‌یکی بررسی کنیم:

```python
for log in logs:
    ...
```

این روش کار می‌کند، اما در بدترین حالت مجبور می‌شویم تمام لاگ‌ها را بررسی کنیم:

```text
O(n)
```

اما یک ویژگی مهم داده‌های ما این است که:

> timestampها از قبل مرتب شده‌اند.

پس می‌توانیم از Binary Search استفاده کنیم و در هر مرحله تقریباً نصف فضای جست‌وجوی باقی‌مانده را حذف کنیم.

در نتیجه:

```text
O(log n)
```

خواهیم داشت.

برای تعداد کمی log شاید این تفاوت خیلی محسوس نباشد، اما با بزرگ‌تر شدن داده اهمیت آن بیشتر می‌شود.

---

## مثال ۱ — زمان دقیق وجود دارد

ورودی:

```python
target_time = "10:08:12"
```

لاگ‌ها:

```text
Index:  0         1         2         3         4         5
Time:   10:00:01  10:02:15  10:05:40  10:08:12  10:08:48  10:12:33
                                      ↑
```

اولین timestamp که شرط:

```text
timestamp >= "10:08:12"
```

را برقرار می‌کند در index زیر قرار دارد:

```text
3
```

پس خروجی:

```python
3
```

است.

---

## مثال ۲ — Target بین دو Log قرار دارد

ورودی:

```python
target_time = "10:08:15"
```

هیچ لاگی دقیقاً در `10:08:15` وجود ندارد.

دو timestamp اطراف آن:

```text
10:08:12
10:08:48
```

هستند.

`10:08:12` زودتر از زمان موردنظر است.

اما:

```text
10:08:48
```

اولین timestampای است که شرط:

```text
timestamp >= target_time
```

را برقرار می‌کند.

پس خروجی:

```python
4
```

است.

چون:

```python
logs[4]
```

برابر است با:

```python
("10:08:48", "Server warning")
```

---

## مثال ۳ — Target قبل از تمام Logهاست

ورودی:

```python
target_time = "09:30:00"
```

اولین log موجود:

```text
10:00:01
```

خودش بعد از زمان موردنظر است.

پس اولین جواب معتبر همان index صفر است:

```python
0
```

---

## مثال ۴ — Target بعد از تمام Logهاست

ورودی:

```python
target_time = "23:00:00"
```

هیچ timestampای شرط:

```text
timestamp >= "23:00:00"
```

را برقرار نمی‌کند.

پس خروجی:

```python
None
```

خواهد بود.

---

## مثال ۵ — Timestampهای تکراری

حالا یک حالت مهم‌تر را در نظر بگیریم:

```python
logs = [
    ("10:00:00", "Server started"),
    ("10:05:00", "Request A"),
    ("10:05:00", "Request B"),
    ("10:05:00", "Request C"),
    ("10:10:00", "Server warning"),
]
```

ورودی:

```python
target_time = "10:05:00"
```

اینجا سه timestamp یکسان داریم.

اما مسئله از ما **اولین log معتبر** را می‌خواهد.

پس خروجی باید:

```python
1
```

باشد.

این edge case یک نکته‌ی مهم را نشان می‌دهد:

> پیدا کردن یکی از matchها کافی نیست؛ باید اولین یا چپ‌ترین match معتبر را پیدا کنیم.

---

## از Exact Search به Boundary Search

در Binary Search ساده معمولاً سؤال این است:

> آیا این مقدار دقیق داخل داده وجود دارد؟

اما اینجا سؤال کمی متفاوت است:

> محدوده‌ی مقادیر معتبر از کجا شروع می‌شود؟

شرط ما:

```text
timestamp >= target_time
```

است.

پس دنبال چپ‌ترین جایی هستیم که این شرط از آنجا به بعد برقرار می‌شود.

به‌صورت مفهومی:

```text
خیلی زود          معتبر
   ↓                ↓

10:00  10:05  10:08  10:12  10:20
                ↑
         اولین مقدار معتبر
```

این نوع جست‌وجو معمولاً **Lower Bound** نامیده می‌شود.

---

## ایده‌ی Candidate

فرض کنیم در یکی از مراحل Binary Search به مقداری برسیم که:

```text
guess >= target_time
```

باشد.

پس log فعلی یک جواب معتبر است.

اما هنوز یک سؤال باقی می‌ماند:

> آیا یک جواب معتبر زودتر از این هم در سمت چپ وجود دارد؟

به همین دلیل نباید فوراً `return` کنیم.

ابتدا index فعلی را به‌عنوان:

```text
candidate
```

ذخیره می‌کنیم.

بعد جست‌وجو را در سمت چپ ادامه می‌دهیم.

به‌صورت مفهومی:

```text
guess >= target

      ↓

این index معتبر است

      ↓

ذخیره در candidate

      ↓

جست‌وجو در سمت چپ
برای پیدا کردن جواب زودتر
```

اگر candidate بهتری پیدا کنیم، مقدار قبلی را جایگزین می‌کنیم.

---

## تصمیم‌های Binary Search

برای حل این مسئله در واقع فقط به دو حالت اصلی نیاز داریم.

### حالت اول — Guess زودتر از Target است

اگر:

```text
guess < target_time
```

باشد، مقدار فعلی نمی‌تواند جواب باشد.

از آنجایی که داده مرتب است، تمام مقادیر سمت چپ آن نیز زودتر از target هستند.

پس همه‌ی آن قسمت را کنار می‌گذاریم:

```python
low = mid + 1
```

---

### حالت دوم — Guess یک جواب معتبر است

اگر:

```text
guess >= target_time
```

باشد، index فعلی می‌تواند جواب باشد.

پس:

```python
candidate = mid
```

اما هنوز ممکن است در سمت چپ یک جواب معتبر زودتر وجود داشته باشد.

بنابراین:

```python
high = mid - 1
```

و جست‌وجو را در نیمه‌ی چپ ادامه می‌دهیم.

این منطق باعث می‌شود timestampهای تکراری هم به‌درستی مدیریت شوند.

## یک اجرای مرحله‌به‌مرحله

فرض کنیم:

```text
target_time = 10:08:15
```

و timestampها این‌ها باشند:

```text
10:00:01
10:02:15
10:05:40
10:08:12
10:08:48
10:12:33
```

### مرحله ۱

مقدار وسط:

```text
10:05:40
```

مقایسه:

```text
10:05:40 < 10:08:15
```

پس این مقدار و تمام مقادیر سمت چپ آن بیش از حد زود هستند.

```text
→ جست‌وجو در سمت راست
```

### مرحله ۲

مقدار وسط بعدی:

```text
10:08:48
```

مقایسه:

```text
10:08:48 >= 10:08:15
```

پس یک جواب معتبر پیدا کرده‌ایم:

```text
candidate = index 4
```

اما شاید در سمت چپ جواب بهتری وجود داشته باشد.

```text
→ جست‌وجو در سمت چپ
```

### مرحله ۳

مقدار بعدی:

```text
10:08:12
```

مقایسه:

```text
10:08:12 < 10:08:15
```

پس:

```text
→ جست‌وجو در سمت راست
```

حالا محدوده‌ی جست‌وجو خالی شده است.

بهترین candidate که پیدا کردیم:

```text
index 4
```

است.

و:

```python
logs[4]
```

برابر است با:

```python
("10:08:48", "Server warning")
```

## چرا مقایسه‌ی String برای Timestampها کار می‌کند؟

در این challenge زمان‌ها با فرمت ثابت زیر ذخیره شده‌اند:

```text
HH:MM:SS
```

و تمام بخش‌ها zero-padded هستند.

مثلاً:

```text
"10:05:00" < "10:08:00" < "11:00:00"
```

در چنین شرایطی ترتیب lexicographical رشته‌ها با ترتیب زمانی آن‌ها هماهنگ است.

به همین دلیل در این تمرین می‌توان timestampها را مستقیماً به‌صورت string مقایسه کرد.

اما در یک سیستم واقعی که تاریخ، timezone یا فرمت‌های مختلف وجود دارند، استفاده از `datetime` یا ساختار زمانی مناسب انتخاب امن‌تری خواهد بود.

## پیچیدگی

Binary Search بعد از هر مقایسه تقریباً نصف فضای جست‌وجوی باقی‌مانده را حذف می‌کند.

بنابراین:

```text
Time Complexity: O(log n)
```

همچنین فقط چند متغیر اضافی داریم:

```text
low
high
mid
candidate
```

پس:

```text
Space Complexity: O(1)
```

است.

## Edge Caseها

پیاده‌سازی باید این حالت‌ها را درست مدیریت کند:

- timestamp دقیق وجود داشته باشد؛
- target بین دو timestamp باشد؛
- target قبل از اولین log باشد؛
- target بعد از آخرین log باشد؛
- لیست logها خالی باشد؛
- فقط یک log وجود داشته باشد؛
- چند timestamp یکسان وجود داشته باشند.

این حالت‌ها باید توسط test suite بررسی شوند.

## چیزی که از این Challenge یاد گرفتم

مهم‌ترین چیزی که از این تمرین می‌گیرم این است که Binary Search فقط یک قطعه کد برای پیدا کردن یک مقدار دقیق نیست.

ایده‌ی عمیق‌تر این است:

> وقتی داده مرتب است، از نتیجه‌ی هر مقایسه استفاده کنم تا بخشی از فضای جست‌وجو را با اطمینان حذف کنم.

در Binary Search ساده ممکن است با دیدن:

```text
guess == target
```

کار تمام شود.

اما اینجا هدف پیدا کردن یک **مرز** است:

```text
value >= target
```

از کدام نقطه شروع به برقرار شدن می‌کند؟

همین تفاوت کوچک باعث می‌شود نحوه‌ی حرکت `low` و `high` هم تغییر کند.

متغیر `candidate` هم اجازه می‌دهد یک جواب معتبر را نگه دارم، ولی همچنان دنبال جواب زودتر و بهتر بگردم.

## نکته‌ی اصلی

Binary Search ساده می‌پرسد:

> این مقدار دقیق کجاست؟

این challenge می‌پرسد:

> اولین مقداری که حداقل به اندازه‌ی target است کجاست؟

این تغییر کوچک، Binary Search را از یک تمرین ساده‌ی جست‌وجو به یک الگوی کاربردی برای **Boundary Search** تبدیل می‌کند.

و چون داده همچنان مرتب است، این کار را می‌توان با:

```text
O(log n)
```

انجام داد.
