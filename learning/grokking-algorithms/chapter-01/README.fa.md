## ۱. جست‌وجوی دودویی

Binary Search یک الگوریتم جست‌وجوی کارآمد برای پیدا کردن یک عنصر در یک **مجموعه‌ی مرتب‌شده** است.

به‌جای اینکه تمام عناصر را یکی‌یکی بررسی کند، ابتدا عنصر وسط را بررسی می‌کند و بعد از هر مقایسه تقریباً نصف فضای جست‌وجوی باقی‌مانده را حذف می‌کند.

مثلاً آرایه‌ی زیر را در نظر بگیریم:

```text
[5, 10, 15, 20, 25, 30, 35]
```

می‌خواهیم مقدار زیر را پیدا کنیم:

```text
25
```

Binary Search ابتدا مقدار وسط را بررسی می‌کند:

```text
[5, 10, 15, 20, 25, 30, 35]
            ↑
           20
```

چون:

```text
20 < 25
```

می‌توانیم نیمه‌ی سمت چپ را کنار بگذاریم.

محدوده‌ی جست‌وجو می‌شود:

```text
[25, 30, 35]
```

مقدار وسط بعدی:

```text
30
```

است.

چون:

```text
30 > 25
```

قسمت سمت راست حذف می‌شود.

در نهایت فقط:

```text
25
```

باقی می‌ماند و مقدار موردنظر پیدا می‌شود.

---

## ۲. Binary Search به داده‌ی مرتب نیاز دارد

Binary Search فقط زمانی درست کار می‌کند که داده‌ها مرتب باشند.

مثلاً:

```text
[2, 5, 8, 12, 17, 21, 30]
```

برای Binary Search مناسب است.

اما:

```text
[21, 5, 30, 2, 17, 8, 12]
```

مناسب نیست.

دلیل این موضوع این است که Binary Search با مقایسه‌ی مقدار موردنظر با عنصر وسط تصمیم می‌گیرد کدام نصف مجموعه را حذف کند.

اگر ترتیب مشخصی وجود نداشته باشد، نمی‌توانیم با اطمینان تصمیم بگیریم کدام قسمت را کنار بگذاریم.

## ۳. مشخص کردن محدوده‌ی جست‌وجو

در پیاده‌سازی Binary Search از دو متغیر برای مشخص کردن محدوده‌ی فعلی جست‌وجو استفاده می‌کنیم:

```python
low = 0
high = len(arr) - 1
```

`low` اولین indexای است که هنوز ممکن است target در آن قرار داشته باشد.

`high` آخرین indexای است که هنوز ممکن است target در آن قرار داشته باشد.

در ابتدای الگوریتم، کل آرایه داخل محدوده‌ی جست‌وجو قرار دارد.

index وسط با این فرمول محاسبه می‌شود:

```python
mid = (low + high) // 2
```

عملگر `//` در Python تقسیم صحیح انجام می‌دهد؛ بنابراین نتیجه می‌تواند مستقیماً به‌عنوان index استفاده شود.

بعد مقدار وسط را می‌گیریم:

```python
guess = arr[mid]
```

سه حالت داریم.

### مقدار پیدا شده است

```python
if guess == target:
    return mid
```

### مقدار حدس‌زده‌شده بزرگ‌تر از target است

پس target باید در سمت چپ باشد:

```python
high = mid - 1
```

### مقدار حدس‌زده‌شده کوچک‌تر از target است

پس target باید در سمت راست باشد:

```python
low = mid + 1
```

تا زمانی که محدوده‌ی جست‌وجو معتبر باشد، الگوریتم ادامه پیدا می‌کند:

```python
while low <= high:
```

اگر محدوده خالی شود، یعنی target در آرایه وجود ندارد.

## ۴. پیاده‌سازی با Python

```python
def binary_search(arr, target):
    low = 0
    high = len(arr) - 1

    while low <= high:
        mid = (low + high) // 2
        guess = arr[mid]

        if guess == target:
            return mid

        elif guess > target:
            high = mid - 1

        else:
            low = mid + 1

    return None
```

مثال:

```python
numbers = [5, 10, 15, 20, 25, 30, 35]

print(binary_search(numbers, 25))
```

خروجی:

```text
4
```

دلیل اینکه نتیجه `4` است این است که index در Python از صفر شروع می‌شود:

```text
Index:  0   1   2   3   4   5   6
Value:  5  10  15  20  25  30  35
                       ↑
```

## ۵. مقایسه‌ی Simple Search و Binary Search

در Simple Search عناصر را یکی‌یکی بررسی می‌کنیم:

```text
1 → 2 → 3 → 4 → 5 → ...
```

اگر `n` عنصر داشته باشیم، در بدترین حالت ممکن است مجبور شویم هر `n` عنصر را بررسی کنیم.

اما Binary Search بعد از هر مقایسه تقریباً نصف گزینه‌های باقی‌مانده را حذف می‌کند.

مثلاً:

```text
128
↓
64
↓
32
↓
16
↓
8
↓
4
↓
2
↓
1
```

فقط هفت بار نصف کردن لازم است.

پس:

```text
Simple Search  → حداکثر n بررسی
Binary Search  → حداکثر log₂(n) بررسی
```

## ۶. لگاریتم

لگاریتم را می‌توان معکوس توان در نظر گرفت.

مثلاً:

```text
2³ = 8
```

بنابراین:

```text
log₂(8) = 3
```

همچنین:

```text
2¹⁰ = 1024
```

پس:

```text
log₂(1024) = 10
```

در این فصل وقتی از `log n` صحبت می‌شود، منظور `log₂(n)` است.

یک روش ساده برای درک آن این است که بپرسیم:

> چند بار می‌توانیم `n` را بر ۲ تقسیم کنیم تا فقط یک گزینه باقی بماند؟

مثلاً:

```text
16
↓
8
↓
4
↓
2
↓
1
```

چهار بار تقسیم انجام شده است.

پس:

```text
log₂(16) = 4
```

همین موضوع دلیل logarithmic بودن Binary Search است.

## ۷. زمان اجرای الگوریتم

هنگام تحلیل الگوریتم، سؤال اصلی فقط این نیست:

> اجرای این برنامه الآن چند ثانیه طول می‌کشد؟

سؤال مهم‌تر این است:

> وقتی اندازه‌ی ورودی بیشتر می‌شود، مقدار کاری که الگوریتم باید انجام دهد چگونه رشد می‌کند؟

مثلاً برای ۱۰۰ عنصر:

```text
Simple Search → حداکثر 100 بررسی
Binary Search → حدود 7 بررسی
```

اما برای تقریباً یک میلیارد عنصر:

```text
Simple Search → حداکثر 1,000,000,000 بررسی
Binary Search → حدود 30 بررسی
```

هرچه ورودی بزرگ‌تر شود، تفاوت بسیار بیشتر می‌شود.

## ۸. Big O Notation

Big O نشان می‌دهد زمان اجرای الگوریتم با بزرگ شدن اندازه‌ی ورودی چگونه رشد می‌کند.

Big O نمی‌گوید یک الگوریتم دقیقاً چند ثانیه طول می‌کشد.

بلکه **نرخ رشد مقدار کار الگوریتم** را توصیف می‌کند.

برای Simple Search:

```text
n عنصر
→ حداکثر n بررسی
```

پس:

```text
O(n)
```

برای Binary Search:

```text
n عنصر
→ حدود log₂(n) بررسی
```

پس:

```text
O(log n)
```

در نتیجه:

```text
Simple Search  → O(n)
Binary Search  → O(log n)
```

---

## ۹. نرخ رشد از یک Benchmark کوچک مهم‌تر است

ممکن است دو الگوریتم روی داده‌های کوچک اختلاف زیادی نداشته باشند.

اما این به این معنا نیست که وقتی ورودی بزرگ شود نیز همین نسبت حفظ خواهد شد.

مثلاً:

```text
اندازه ورودی       Simple Search       Binary Search

100                100                 ~7
1,000              1,000               ~10
1,000,000          1,000,000           ~20
1,000,000,000      1,000,000,000       ~30
```

Binary Search در مقایسه با Simple Search بسیار آهسته‌تر رشد می‌کند.

به همین دلیل شناخت **نرخ رشد** الگوریتم از مقایسه‌ی یک زمان اجرای کوچک مهم‌تر است.

---

## ۱۰. تحلیل بدترین حالت

در این فصل Big O برای توصیف رشد الگوریتم در بدترین حالت استفاده می‌شود.

فرض کنیم با Simple Search دنبال یک اسم در دفترچه تلفن هستیم.

اگر اسم موردنظر اولین اسم باشد، در همان بررسی اول پیدا می‌شود.

این بهترین حالت است.

اما ممکن است اسم موردنظر آخرین ورودی دفترچه باشد.

در آن صورت باید تمام عناصر را بررسی کنیم.

بنابراین پیچیدگی بدترین حالت همچنان:

```text
O(n)
```

است.

در این فصل تمرکز اصلی بر Worst Case است.

Average Case در فصل‌های بعدی کتاب بررسی می‌شود.

---

## ۱۱. پیچیدگی‌های رایج Big O

چند پیچیدگی رایج، از رشد بهتر به رشد بدتر:

```text
O(log n)
O(n)
O(n log n)
O(n²)
O(n!)
```

### `O(log n)` — زمان لگاریتمی

مثال:

```text
Binary Search
```

فضای جست‌وجو مرتباً کوچک می‌شود.

---

### `O(n)` — زمان خطی

مثال:

```text
Simple Search
```

با افزایش اندازه‌ی ورودی، مقدار کار تقریباً به همان نسبت افزایش پیدا می‌کند.

---

### `O(n log n)`

این نوع رشد در الگوریتم‌های مرتب‌سازی سریع دیده می‌شود.

از `O(n)` سریع‌تر رشد می‌کند، اما برای داده‌های بزرگ بسیار بهتر از `O(n²)` مقیاس می‌گیرد.

---

### `O(n²)` — زمان درجه دوم

این نوع رشد در الگوریتم‌هایی مانند Selection Sort دیده می‌شود که در فصل بعد بررسی خواهد شد.

مثلاً:

```text
n = 10
n² = 100
```

اما:

```text
n = 1000
n² = 1,000,000
```

پس مقدار کار با سرعت زیادی افزایش پیدا می‌کند.

---

### `O(n!)` — زمان فاکتوریلی

رشد فاکتوریلی بسیار سریع است.

مثلاً:

```text
5! = 120
6! = 720
7! = 5,040
8! = 40,320
10! = 3,628,800
```

با اضافه شدن تنها چند ورودی، تعداد عملیات می‌تواند بسیار بزرگ شود.

---

## ۱۲. مسئله‌ی فروشنده‌ی دوره‌گرد

Traveling Salesperson Problem نمونه‌ای برای نشان دادن رشد فاکتوریلی است.

فرض کنیم یک فروشنده باید از چند شهر عبور کند و می‌خواهد کوتاه‌ترین مسیر ممکن را پیدا کند.

یک راه Brute Force این است که:

1. تمام ترتیب‌های ممکن شهرها را تولید کنیم.
2. فاصله‌ی کل هر مسیر را محاسبه کنیم.
3. تمام مسیرها را مقایسه کنیم.
4. کوتاه‌ترین مسیر را انتخاب کنیم.

برای پنج شهر:

```text
5! = 120
```

ترتیب ممکن وجود دارد.

برای شش شهر:

```text
6! = 720
```

و برای هفت شهر:

```text
7! = 5,040
```

در حالت کلی، بررسی تمام ترتیب‌های ممکن رشد:

```text
O(n!)
```

دارد.

این روش با بزرگ شدن ورودی خیلی سریع غیرعملی می‌شود.

در فصل‌های بعدی کتاب روش‌های تقریبی برای چنین مسائل دشواری بررسی می‌شوند.

## ۱۴. تست پیاده‌سازی

پیاده‌سازی Binary Search این پروژه با `pytest` تست می‌شود.

حالت‌های مهمی که باید بررسی شوند:

* وجود target
* اولین عنصر
* آخرین عنصر
* عدم وجود target
* آرایه‌ی خالی
* آرایه‌ی تک‌عنصری
* آرایه‌ی تک‌عنصری که target در آن وجود ندارد

مثال:

```python
def test_target_exists():
    arr = [5, 10, 15, 20, 25, 30, 35]

    result = binary_search(arr, 25)

    assert result == 4
```

هدف تست این است که مطمئن شویم الگوریتم هم در حالت‌های عادی و هم در Edge Caseها رفتار درستی دارد.

مهم‌ترین درس این فصل فقط نحوه‌ی نوشتن Binary Search نیست.

سؤال مهم‌تری که از این به بعد باید هنگام دیدن یک الگوریتم بپرسیم این است:

> **اگر اندازه‌ی ورودی خیلی بزرگ‌تر شود، رفتار این الگوریتم چگونه تغییر می‌کند؟**

این سؤال یکی از پایه‌های اصلی تحلیل الگوریتم‌ها است.

```text
Binary Search → O(log n)

Simple Search → O(n)
```

هرچه ورودی بزرگ‌تر شود، اهمیت تفاوت بین این دو نرخ رشد بیشتر می‌شود.
