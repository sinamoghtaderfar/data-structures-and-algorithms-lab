# مبانی ساختمان داده

این فایل یادداشت پایه‌ی من برای **ساختمان داده‌ها و پیچیدگی الگوریتمی** است.

قرار نیست اینجا یک کتاب کامل علوم کامپیوتر بنویسم یا همه‌ی ساختمان داده‌ها را از صفر پیاده‌سازی کنم. هدفم ساده‌تر و کاربردی‌تر است: می‌خواهم از ساختارهایی که مرتب در الگوریتم‌ها می‌بینم یک تصویر ذهنی درست داشته باشم، تفاوت‌هایشان را بفهمم و بدانم چرا در یک مسئله ممکن است یک ساختار انتخاب بهتری از ساختار دیگر باشد.

در بخش‌های بعدی این repository، خیلی از این مفاهیم را جداگانه و عمیق‌تر پیاده‌سازی و بررسی می‌کنم.

---

## ۱. ساختمان داده و الگوریتم چه فرقی دارند؟

**Data Structure** روشی برای سازمان‌دهی و نگهداری داده است.

**Algorithm** مجموعه‌ای از مراحل برای حل یک مسئله است.

این دو به هم وابسته‌اند، ولی کار یکسانی انجام نمی‌دهند.

ساختمان داده به سؤال‌هایی مثل این پاسخ می‌دهد:

* داده را چطور نگه دارم؟
* چطور به آن دسترسی پیدا کنم؟
* اضافه یا حذف کردن داده چقدر هزینه دارد؟
* روابط میان داده‌ها را چطور نمایش بدهم؟
* کدام عملیات باید سریع باشند؟

اما الگوریتم بیشتر به این سؤال جواب می‌دهد:

> برای رسیدن به نتیجه، چه مراحلی را باید اجرا کنم؟

مثلاً داده‌ی زیر را در نظر بگیر:

```text
[10, 20, 30, 40, 50]
```

این دنباله خودش یک روش برای سازمان‌دهی داده است.

اگر از قبل بدانم که عنصر index شماره‌ی `3` را می‌خواهم، مستقیماً به:

```text
40
```

دسترسی پیدا می‌کنم.

اما اگر فقط بدانم که دنبال مقدار `40` هستم، به یک روش جستجو نیاز دارم.

پس یکی از مهم‌ترین مدل‌های ذهنی برای من این است:

> **ساختمان داده مشخص می‌کند داده چگونه سازمان‌دهی شود؛ الگوریتم مشخص می‌کند با آن داده چه کاری انجام شود.**

انتخاب درست این دو کنار هم می‌تواند یک راه‌حل را هم ساده‌تر و هم بسیار سریع‌تر کند.

## ۲. یک مرور کوتاه روی Complexity

قبل از مقایسه‌ی ساختمان داده‌ها باید یک روش داشته باشم تا بفهمم هزینه‌ی عملیات با بزرگ‌تر شدن داده‌ها چگونه رشد می‌کند.

اینجاست که **Big O** وارد می‌شود.

چند پیچیدگی رایج:

| Complexity   | ایده‌ی ساده                                                      |
| ------------ | ---------------------------------------------------------------- |
| `O(1)`       | مقدار کار تقریباً ثابت است                                       |
| `O(log n)`   | در هر مرحله بخش بزرگی از مسئله حذف می‌شود                        |
| `O(n)`       | مقدار کار تقریباً همراه با تعداد عناصر رشد می‌کند                |
| `O(n log n)` | در الگوریتم‌های sorting خوب زیاد دیده می‌شود                     |
| `O(n²)`      | معمولاً تعداد زیادی عنصر با تعداد زیادی عنصر دیگر مقایسه می‌شوند |

مثلاً:

```text
arr[500]                -> O(1)
پیمایش کل لیست          -> O(n)
Binary Search           -> O(log n)
```

Big O به من نمی‌گوید اجرای کد دقیقاً چند میلی‌ثانیه طول می‌کشد.

Big O می‌گوید:

> وقتی اندازه‌ی ورودی بزرگ‌تر شد، مقدار کار با چه سرعتی رشد می‌کند؟

این تفاوت مهم است.

## ۳. Array و Python List

Array مجموعه‌ای از مقادیر را به‌صورت یک دنباله‌ی مرتب نگهداری می‌کند.

از نظر ذهنی:

```text
Index:   0   1   2   3
Value:  10  20  30  40
```

اگر index را بدانم، می‌توانم مستقیماً سراغ عنصر موردنظر بروم:

```python
numbers = [10, 20, 30, 40]

print(numbers[2])
```

خروجی:

```text
30
```

### `list` در Python دقیقاً چیست؟

نکته‌ای که برای من مهم است این است که `list` در Python در اصل یک **Dynamic Array** است.

یعنی دقیقاً مثل یک آرایه‌ی ثابت و سطح پایین در C نیست، اما همچنان ویژگی مهم آرایه را دارد:

```text
دسترسی سریع با index
```

پس این:

```python
numbers = [10, 20, 30]
```

را نباید از نظر ساختار داخلی با Linked List اشتباه بگیرم.

### دسترسی با Index

عملیاتی مثل:

```python
numbers[2]
```

معمولاً:

```text
O(1)
```

است.

یعنی Python لازم نیست برای رسیدن به عنصر سوم، ابتدا عناصر صفر، یک و دو را پیمایش کند.

### Search

اما اگر index را ندانم و فقط دنبال یک مقدار باشم:

```text
[3, 8, 12, 19, 25]

Find 19:

3 → 8 → 12 → 19
```

ممکن است مجبور شوم عناصر را یکی‌یکی بررسی کنم.

در این حالت جستجوی خطی:

```text
O(n)
```

است.

پس یک Array می‌تواند برای دسترسی با index بسیار سریع باشد، ولی جستجو داخل آن الزاماً سریع نیست.

### Insert و Delete

اگر وسط یک Array چیزی اضافه کنم:

```text
Before:

[10, 20, 30, 40]

Insert 15:

[10, 15, 20, 30, 40]
```

ممکن است چند عنصر مجبور شوند جابه‌جا شوند.

همین موضوع باعث می‌شود اضافه یا حذف کردن از وسط، نسبت به access مستقیم هزینه‌ی بیشتری داشته باشد.

### مدل ذهنی

Array را این‌طور تصور می‌کنم:

> **یک ردیف جعبه‌ی شماره‌گذاری‌شده.**

اگر شماره‌ی جعبه را بدانم، مستقیم می‌روم سراغ همان جعبه.

## ۴. Linked List

Linked List هم یک دنباله از داده‌ها را نگهداری می‌کند، ولی اتصال عناصر آن با Array متفاوت است.

Linked List از **Node**ها تشکیل شده است.

مثلاً:

```text
[10] → [20] → [30] → [40] → None
```

هر Node معمولاً حداقل این دو بخش را دارد:

```text
value
next
```

مثلاً:

```text
Node
├── value: 20
└── next: reference to next node
```

### Traversal

اگر بخواهم به Node چهارم برسم، معمولاً نمی‌توانم مستقیماً بپرم روی آن.

باید مسیر را دنبال کنم:

```text
10 → 20 → 30 → 40
```

به همین دلیل دسترسی به یک موقعیت دلخواه معمولاً:

```text
O(n)
```

است.

### Insert

فرض کنیم reference مربوط به `B` را از قبل دارم:

```text
A → B → C
```

می‌توانم `X` را این‌طور اضافه کنم:

```text
A → B → X → C
```

خود تغییر referenceها می‌تواند:

```text
O(1)
```

باشد.

اما یک نکته‌ی مهم وجود دارد:

> اگر ابتدا مجبور باشم `B` را پیدا کنم، پیدا کردن آن هنوز ممکن است `O(n)` زمان بگیرد.

این تفاوت را نباید فراموش کنم.

### Array در برابر Linked List

| عملیات                       |                        Dynamic Array |          Linked List |
| ---------------------------- | -----------------------------------: | -------------------: |
| دسترسی با index              |                               `O(1)` |               `O(n)` |
| Search                       |                               `O(n)` |               `O(n)` |
| Insert/Delete در Node مشخص   | ممکن است نیاز به shifting داشته باشد | می‌تواند `O(1)` باشد |
| Memory locality              |                         معمولاً بهتر |      معمولاً ضعیف‌تر |
| حافظه‌ی اضافه برای reference |                                   کم |   برای Node لازم است |

### مدل ذهنی

Linked List را این‌طور تصور می‌کنم:

> **یک زنجیره که هر حلقه آدرس حلقه‌ی بعدی را می‌داند.**

برای رسیدن به حلقه‌ی شماره‌ی 500، معمولاً باید مسیر را طی کنم.

## ۵. Stack

Stack از قانون زیر پیروی می‌کند:

```text
LIFO
```

یعنی:

> **Last In, First Out**

آخرین چیزی که وارد شده، اولین چیزی است که خارج می‌شود.

مثال کلاسیکش یک دسته بشقاب است:

```text
Top
 ↓
 C
 B
 A
```

`C` آخر از همه اضافه شده، پس اول از همه خارج می‌شود.

### عملیات اصلی

Push:

```text
اضافه کردن به بالای Stack
```

Pop:

```text
برداشتن عنصر بالای Stack
```

Peek:

```text
دیدن عنصر بالایی بدون حذف کردن آن
```

### مثال Python

```python
stack = []

stack.append("A")
stack.append("B")
stack.append("C")

item = stack.pop()

print(item)
```

خروجی:

```text
C
```

### Stack کجا استفاده می‌شود؟

مثلاً در:

* function calls
* recursion
* undo
* expression parsing
* DFS
* backtracking

### مدل ذهنی

> **آخرین کار ناتمام، زودتر از همه بررسی می‌شود.**

---

## ۶. Queue

Queue تقریباً نقطه‌ی مقابل Stack است.

قانون آن:

```text
FIFO
```

یعنی:

> **First In, First Out**

مثلاً:

```text
Front                 Back
  ↓                     ↓

A → B → C → D
```

`A` زودتر وارد شده، پس زودتر هم خارج می‌شود.

### عملیات اصلی

Enqueue:

```text
اضافه کردن به انتهای Queue
```

Dequeue:

```text
برداشتن از ابتدای Queue
```

### Queue در Python

برای Queue واقعی در Python معمولاً `collections.deque` انتخاب بهتری از `list.pop(0)` است.

```python
from collections import deque

queue = deque()

queue.append("A")
queue.append("B")
queue.append("C")

first = queue.popleft()

print(first)
```

خروجی:

```text
A
```

### Queue کجا استفاده می‌شود؟

مثلاً:

* task scheduling
* message queues
* request handling
* print jobs
* BFS

### Stack vs Queue

```text
Stack -> LIFO
Queue -> FIFO
```

همین تفاوت ساده در بسیاری از الگوریتم‌ها نقش بسیار مهمی دارد.

## ۷. Hash Table

Hash Table داده‌ها را به‌صورت:

```text
key → value
```

نگهداری می‌کند.

مثلاً:

```text
name → Sina
city → Bamberg
role → developer
```

در Python، `dict` بر اساس همین ایده ساخته شده است:

```python
user = {
    "name": "Sina",
    "city": "Bamberg",
}

print(user["name"])
```

خروجی:

```text
Sina
```

### چرا Hash Table مهم است؟

فرض کنیم:

```python
prices = {
    "apple": 2.50,
    "banana": 1.80,
    "orange": 2.10,
}
```

اگر قیمت Apple را بخواهم:

```python
prices["apple"]
```

مفهومی که اینجا مهم است این است که لازم نیست همه‌ی محصولات را یکی‌یکی بررسی کنم.

### Hash Function

خیلی ساده:

```text
key
 ↓
hash function
 ↓
internal location
```

Hash Function کمک می‌کند مشخص شود داده مربوط به یک key کجا قرار بگیرد یا از کجا پیدا شود.

### Complexity

Lookup، insert و delete در حالت average معمولاً:

```text
O(1)
```

هستند.

ولی این تضمین نمی‌کند که در تمام شرایط ممکن همیشه دقیقاً `O(1)` باقی بمانند.

در بدترین حالت، عملکرد می‌تواند تا:

```text
O(n)
```

افت کند.

### Collision

گاهی دو key متفاوت ممکن است به یک محل داخلی مشابه برسند.

به این اتفاق:

```text
Collision
```

گفته می‌شود.

Hash Tableها برای مدیریت collision روش‌های مشخصی دارند.

### مدل ذهنی

> **یک سیستم انبار با برچسب.**

به‌جای اینکه بگویم «عنصر شماره ۵»، می‌گویم «مقدار مربوط به کلید `name` را بده».

## ۸. Tree

Tree برای نمایش داده‌های **سلسله‌مراتبی** مناسب است.

مثلاً:

```text
        A
       / \
      B   C
     / \
    D   E
```

چند مفهوم مهم:

```text
A -> Root
B -> Parent
D -> Child
C, D, E -> Leaf
```

### مثال واقعی

ساختار فولدرها خودش یک Tree است:

```text
projects/
├── backend/
│   ├── api/
│   └── database/
└── frontend/
    ├── components/
    └── pages/
```

### Binary Tree

در Binary Tree هر Node حداکثر دو Child دارد:

```text
       10
      /  \
     5    20
```

### Binary Search Tree

BST علاوه بر Tree بودن، یک قانون ordering هم دارد.

به‌شکل ساده:

```text
smaller values ← node → larger values
```

مثلاً:

```text
        10
       /  \
      5    20
     / \
    2   7
```

فعلاً مهم‌ترین چیزی که باید درباره Tree بفهمم این است:

> وقتی داده ذاتاً ساختار سلسله‌مراتبی دارد، Tree معمولاً مدل طبیعی‌تری نسبت به یک List ساده است.

## ۹. Graph

Graph برای مدل کردن **رابطه میان موجودیت‌ها** استفاده می‌شود.

Graph از دو مفهوم اصلی تشکیل شده است:

```text
Nodes / Vertices
Edges
```

مثلاً:

```text
A ----- B
|       |
|       |
C ----- D
```

### Graph کجا دیده می‌شود؟

مثلاً:

* نقشه‌ی جاده‌ها
* شبکه‌های اجتماعی
* شبکه‌ی کامپیوتری
* dependencyها
* مسیرهای پرواز
* recommendation systems
* linkهای صفحات وب

### Undirected Graph

```text
A ----- B
```

رابطه دوطرفه است.

### Directed Graph

```text
A → B
```

رابطه direction دارد.

مثلاً:

> A می‌تواند B را follow کند، بدون اینکه B حتماً A را follow کرده باشد.

### Weighted Graph

Edge می‌تواند یک مقدار هم داشته باشد:

```text
A --5--> B
```

این `5` ممکن است:

* distance
* cost
* travel time
* latency

باشد.

همین‌جا بعداً الگوریتم‌هایی مثل Dijkstra معنی پیدا می‌کنند.

### مدل ذهنی

> **Nodeها چیزها هستند؛ Edgeها رابطه بین آن چیزها هستند.**

## ۱۰. مقایسه سریع

| Structure     | نقطه قوت اصلی             | رفتار مهم                               |
| ------------- | ------------------------- | --------------------------------------- |
| Dynamic Array | دسترسی سریع با index      | Access `O(1)`                           |
| Linked List   | ارتباط انعطاف‌پذیر Nodeها | Access `O(n)`                           |
| Stack         | پردازش LIFO               | Push/Pop `O(1)`                         |
| Queue         | پردازش FIFO               | Enqueue/Dequeue `O(1)` با ساختار مناسب  |
| Hash Table    | Lookup سریع با Key        | Average `O(1)`                          |
| Tree          | نمایش hierarchy           | بستگی به نوع Tree دارد                  |
| Graph         | نمایش relationshipها      | بستگی به الگوریتم و representation دارد |

هیچ Data Structureای در همه‌ی شرایط بهترین نیست.

سؤال مهم‌تر این است:

> **در این مسئله کدام عملیات برای من مهم‌تر است؟**

یک ساختار ممکن است access فوق‌العاده‌ای داشته باشد ولی insertion ضعیف‌تری داشته باشد.

یکی دیگر ممکن است برای روابط پیچیده عالی باشد ولی برای indexed access اصلاً مناسب نباشد.

همه‌چیز trade-off است.

## ۱۱. چیزهایی که می‌خواهم از این بخش یادم بماند

اگر جزئیات را فراموش کردم، حداقل این تصویر ذهنی باید بماند:

```text
Array       -> جعبه‌های شماره‌گذاری‌شده
Linked List -> Nodeهای متصل به هم
Stack       -> LIFO
Queue       -> FIFO
Hash Table  -> key → value
Tree        -> hierarchy
Graph       -> relationships
```

اما مهم‌تر از حفظ این تعریف‌ها:

> **انتخاب Data Structure یعنی انتخاب trade-off مناسب برای مسئله.**

سرعت access، سرعت insertion، memory، ترتیب داده‌ها و نوع relationship همگی روی این تصمیم اثر دارند.
