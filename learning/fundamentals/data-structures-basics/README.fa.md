# مبانی ساختمان داده

[English](./README.md) | **فارسی**

این‌ها یادداشت‌های من درباره‌ی ساختمان‌داده‌های پایه و مفاهیم اولیه‌ی پیچیدگی هستند؛ چیزهایی که می‌خواهم قبل از ورود عمیق‌تر به الگوریتم‌ها درک درستی از آن‌ها داشته باشم.

هدف این نوشته این نیست که تمام جزئیات ساختمان داده را پوشش دهد یا همه‌ی آن‌ها را از صفر پیاده‌سازی کند. هدف این است که یک تصویر ذهنی روشن از مهم‌ترین ساختارها داشته باشم، بدانم چگونه کار می‌کنند و چرا در شرایط مختلف ممکن است یکی را به دیگری ترجیح دهم.

در ادامه‌ی این مخزن، بسیاری از این مفاهیم را به‌صورت عمیق‌تر مطالعه و پیاده‌سازی خواهم کرد.

---

## 1. ساختمان داده چیست؟

**ساختمان داده (Data Structure)** روشی برای سازمان‌دهی و نگهداری داده‌هاست تا بتوانیم به شکل مناسبی با آن‌ها کار کنیم.

برنامه‌ها دائماً با انواع مختلف داده سروکار دارند:

* کاربران
* محصولات
* پیام‌ها
* اعداد
* فایل‌ها
* وظایف
* موقعیت‌ها
* ارتباط میان اشیا

نحوه‌ی سازمان‌دهی این داده‌ها روی سرعت و سادگی کار با آن‌ها تأثیر مستقیم دارد.

برای مثال، فرض کنیم یک میلیون شناسه‌ی کاربر داریم و می‌خواهیم یک شناسه‌ی خاص را پیدا کنیم.

بسته به اینکه داده‌ها چگونه ذخیره شده باشند و از چه الگوریتمی استفاده کنیم، این جستجو می‌تواند بسیار سریع یا به شکل غیرضروری کند باشد.

به همین دلیل ساختمان داده و الگوریتم ارتباط نزدیکی با یکدیگر دارند.

یک ساختمان داده به سؤال‌هایی مانند این پاسخ می‌دهد:

* داده‌ها را چگونه ذخیره کنم؟
* چگونه به آن‌ها دسترسی داشته باشم؟
* چگونه در میان آن‌ها جستجو کنم؟
* چگونه داده‌ی جدید اضافه کنم؟
* چگونه داده‌ای را حذف کنم؟

اما الگوریتم به سؤال دیگری پاسخ می‌دهد:

> برای حل یک مسئله باید چه مراحلی را طی کنم؟

### مثال ساده

فرض کنیم داده‌های زیر را داریم:

```text
[10, 20, 30, 40, 50]
```

این داده‌ها به شکل یک دنباله ذخیره شده‌اند.

اگر بخواهم عنصر سوم را بردارم، ساختمان داده امکان دسترسی به آن را از طریق موقعیتش فراهم می‌کند.

اما اگر بخواهم مقدار `40` را پیدا کنم، به یک روش یا الگوریتم جستجو نیاز دارم.

پس به زبان ساده:

> **ساختمان داده، داده‌ها را سازمان‌دهی می‌کند و الگوریتم روی آن داده‌ها عملیات انجام می‌دهد.**

# 2. آرایه‌ها و لیست‌ها

آرایه یکی از پایه‌ای‌ترین ساختمان داده‌هاست.

آرایه چند مقدار را به‌صورت یک دنباله‌ی مرتب نگهداری می‌کند.

مثلاً:

```text
[10, 20, 30, 40]
```

هر عنصر دارای یک موقعیت به نام **Index** است.

```text
Index:   0   1   2   3
Value:  10  20  30  40
```

بنابراین مقدار موجود در index شماره‌ی `2` برابر است با:

```text
30
```

در Python معمولاً با `list` کار می‌کنیم:

```python
numbers = [10, 20, 30, 40]

print(numbers[2])
```

خروجی:

```text
30
```

لیست‌های Python دقیقاً همان آرایه‌های ثابت و سطح پایین در زبان‌هایی مثل C و C++ نیستند، اما برای بسیاری از کاربردها رفتار مشابهی به‌عنوان یک دنباله‌ی قابل دسترسی با index دارند.

## چرا Array مفید است؟

Array و List زمانی مناسب هستند که:

* ترتیب داده‌ها مهم باشد.
* بخواهیم با موقعیت عناصر به آن‌ها دسترسی داشته باشیم.
* تعداد زیادی مقدار مشابه داشته باشیم.
* بخواهیم مرتب روی تمام عناصر حرکت کنیم.

مثلاً:

```text
temperatures
user IDs
scores
product prices
coordinates
```

## Access

دسترسی به یک عنصر با استفاده از index بسیار سریع است.

```python
numbers[3]
```

در یک ساختار آرایه‌مانند، این عملیات معمولاً:

```text
O(1)
```

است.

یعنی بزرگ‌تر شدن آرایه تعداد مراحل لازم برای دسترسی به یک index مشخص را به شکل قابل توجهی افزایش نمی‌دهد.

## Search

اگر موقعیت یک مقدار را ندانیم، ممکن است مجبور شویم عناصر را یکی‌یکی بررسی کنیم.

```text
[3, 8, 12, 19, 25]

Find 19:

3 → 8 → 12 → 19
```

یک جستجوی خطی ساده ممکن است به:

```text
O(n)
```

عملیات نیاز داشته باشد.

## Insert و Delete

اضافه یا حذف کردن یک مقدار گاهی هزینه‌ی بیشتری دارد، زیرا ممکن است لازم باشد عناصر دیگر جابه‌جا شوند.

مثلاً:

```text
Before:

[10, 20, 30, 40]

Insert 15:

[10, 15, 20, 30, 40]
```

برای ایجاد فضای جدید ممکن است چند عنصر جابه‌جا شوند.

جزئیات دقیق این رفتار به زبان برنامه‌نویسی و نوع پیاده‌سازی بستگی دارد.

## مدل ذهنی

من Array را این‌گونه تصور می‌کنم:

> یک ردیف از جعبه‌های شماره‌گذاری‌شده.

اگر شماره‌ی جعبه را بدانم، می‌توانم مستقیماً سراغ همان جعبه بروم.

## نکته‌ی اصلی

Arrayها زمانی بسیار مناسب هستند که به موارد زیر نیاز داشته باشم:

* داده‌ی مرتب
* دسترسی سریع با index
* پیمایش ساده‌ی عناصر

# 3. Linked List

**Linked List** نیز یک دنباله از مقادیر را نگهداری می‌کند، اما ساختارش با Array متفاوت است.

به‌جای اینکه موقعیت عناصر نقش اصلی را داشته باشد، Linked List از اجزایی به نام **Node** ساخته شده است.

یک Linked List ساده می‌تواند این شکل را داشته باشد:

```text
[10] → [20] → [30] → [40]
```

هر Node معمولاً حداقل دو چیز دارد:

```text
value
next
```

برای مثال:

```text
Node
├── value: 20
└── next: reference to node containing 30
```

یعنی Nodeها مانند حلقه‌های یک زنجیر به یکدیگر متصل هستند.

## Node چیست؟

Node یک عنصر از یک ساختمان داده است.

مثلاً:

```text
[10] → [20] → [30]
```

در اینجا سه Node داریم.

هر Node مقداری را نگه می‌دارد و معمولاً به Node بعدی اشاره می‌کند.

## Traversal

در Array معمولاً می‌توانیم مستقیماً بگوییم:

```text
element at index 500
```

اما در یک Linked List معمولی برای رسیدن به یک عنصر باید از ابتدا شروع کنیم و لینک‌ها را دنبال کنیم:

```text
10 → 20 → 30 → 40
```

به این کار **Traversal** یا پیمایش گفته می‌شود.

بنابراین رسیدن به یک عنصر از طریق موقعیتش ممکن است نیازمند:

```text
O(n)
```

زمان باشد.

## چرا از Linked List استفاده می‌کنیم؟

Linked List می‌تواند زمانی مفید باشد که عناصر به‌صورت پویا به یکدیگر متصل باشند و بخواهیم در یک موقعیت مشخص بدون جابه‌جایی تعداد زیادی عنصر، Node جدیدی اضافه یا حذف کنیم.

مثلاً:

```text
A → B → C
```

اگر reference مناسب را داشته باشیم، اضافه کردن `X` میان `B` و `C` می‌تواند به شکل زیر انجام شود:

```text
A → B → X → C
```

به‌جای جابه‌جا کردن تعداد زیادی عنصر، فقط ارتباط میان Nodeها تغییر می‌کند.

## Array در برابر Linked List

یک مقایسه‌ی ساده:

| عملیات                       |                                 Array |                      Linked List |
| ---------------------------- | ------------------------------------: | -------------------------------: |
| دسترسی با index              |                                  سریع |                            کندتر |
| پیمایش ترتیبی                |                                 مناسب |                            مناسب |
| Insert/Delete در موقعیت مشخص | ممکن است نیاز به جابه‌جایی داشته باشد |             می‌تواند کارآمد باشد |
| نحوه‌ی قرارگیری در حافظه     |                     معمولاً پیوسته‌تر | Nodeها می‌توانند جدا از هم باشند |

پیاده‌سازی واقعی جزئیات بیشتری دارد، اما در حال حاضر همین مقایسه برای من کافی است.

## مدل ذهنی

Linked List را این‌گونه تصور می‌کنم:

> یک زنجیره که هر حلقه آدرس حلقه‌ی بعدی را می‌داند.

معمولاً نمی‌توانم مستقیماً به Node دهم بپرم؛ باید مسیر را دنبال کنم.

## نکته‌ی اصلی

Linked List مجموعه‌ای از Nodeهای متصل به یکدیگر است.

فعلاً باید این مفاهیم را به خاطر داشته باشم:

* Node
* Value
* Next reference
* Traversal

# 4. Stack

**Stack** ساختمانی است که از قانون زیر پیروی می‌کند:

```text
LIFO
```

یعنی:

> **Last In, First Out**

یا:

> آخرین چیزی که وارد می‌شود، اولین چیزی است که خارج می‌شود.

ساده‌ترین مثال، یک دسته بشقاب است.

اگر بشقاب‌ها را این‌گونه قرار دهیم:

```text
C
B
A
```

بشقاب `C` آخر از همه قرار گرفته است.

پس اولین بشقابی هم هست که برداشته می‌شود.

## عملیات اصلی

### Push

اضافه کردن یک عنصر به بالای Stack.

```text
Before:

B
A

push(C)

After:

C
B
A
```

### Pop

حذف عنصر بالای Stack.

```text
C
B
A

pop()

returns C
```

### Peek / Top

مشاهده‌ی عنصر بالای Stack بدون حذف آن.

## مثال در Python

می‌توان از یک List در Python به‌عنوان Stack ساده استفاده کرد:

```python
stack = []

stack.append("A")
stack.append("B")
stack.append("C")

last_item = stack.pop()

print(last_item)
```

خروجی:

```text
C
```

## کاربردها

Stack در بخش‌های زیادی از برنامه‌نویسی دیده می‌شود.

مثلاً:

* Function calls
* Recursion
* Undo
* Expression parsing
* Syntax processing
* Depth-First Search
* تاریخچه‌ی ناوبری

## Stack و Function Call

وقتی یک function، function دیگری را صدا می‌زند، برنامه باید به خاطر داشته باشد بعد از پایان آن function به کجا برگردد.

این رفتار از نظر مفهومی ارتباط زیادی با Stack دارد.

این موضوع هنگام یادگیری Recursion اهمیت بیشتری پیدا می‌کند.

## مدل ذهنی

Stack را این‌طور تصور می‌کنم:

> جدیدترین کار ناتمام، زودتر از بقیه پردازش می‌شود.

## نکته‌ی اصلی

```text
Stack = LIFO
```

آخرین ورودی، اولین خروجی.

# 5. Queue

**Queue** تقریباً منطق برعکس Stack را دارد:

```text
FIFO
```

یعنی:

> **First In, First Out**

یا:

> اولین چیزی که وارد شده، اولین چیزی است که خارج می‌شود.

بهترین مثال، یک صف واقعی است.

فرض کنیم افراد با این ترتیب وارد صف شوند:

```text
A → B → C → D
```

`A` زودتر از همه آمده است، پس باید زودتر از بقیه سرویس بگیرد.

## عملیات اصلی

### Enqueue

اضافه کردن یک عنصر به انتهای صف.

### Dequeue

برداشتن یک عنصر از ابتدای صف.

به‌صورت مفهومی:

```text
Front                 Back
  ↓                     ↓

A → B → C → D
```

بعد از یک Dequeue:

```text
B → C → D
```

## کاربردها

Queue زمانی مفید است که کارها باید به ترتیب ورود پردازش شوند.

مثلاً:

* Task processing
* Print jobs
* Request handling
* Message processing
* Scheduling
* Breadth-First Search (BFS)

## Stack در برابر Queue

این تفاوت را باید خوب به خاطر داشته باشم:

```text
Stack
Last In → First Out

Queue
First In → First Out
```

## مدل ذهنی

Queue را مثل صف آدم‌ها تصور می‌کنم:

> کسی که زودتر آمده، زودتر سرویس می‌گیرد.

## نکته‌ی اصلی

```text
Queue = FIFO
```

اولین ورودی، اولین خروجی.

# 6. Hash Table

**Hash Table** داده‌ها را به شکل **Key و Value** ذخیره می‌کند.

مثلاً:

```text
name → Sina
city → Bamberg
age  → 25
```

به‌جای اینکه بگوییم:

> عنصر سوم را بده.

می‌توانیم بگوییم:

> مقداری که متعلق به key به نام `name` است را بده.

در Python، `dictionary` نمونه‌ی بسیار مهمی از این مفهوم است.

```python
user = {
    "name": "Sina",
    "city": "Bamberg",
    "age": 25,
}

print(user["name"])
```

خروجی:

```text
Sina
```

## چرا Hash Table مفید است؟

فرض کنیم قیمت محصولات را ذخیره کرده‌ایم:

```python
prices = {
    "apple": 2.50,
    "banana": 1.80,
    "orange": 2.10,
}
```

برای گرفتن قیمت apple:

```python
prices["apple"]
```

لازم نیست تمام محصولات را یکی‌یکی جستجو کنم.

Hash Table برای همین نوع جستجوی سریع طراحی شده است.

## Hash Function

در پشت Hash Table مفهومی به نام **Hash Function** وجود دارد.

به شکل بسیار ساده:

```text
key
 ↓
hash function
 ↓
location
```

Hash Function کمک می‌کند مشخص شود مقدار مربوط به یک key در کجا ذخیره یا پیدا شود.

فعلاً نیازی ندارم جزئیات داخلی آن را کامل بدانم.

ایده‌ی اصلی این است:

> یک Key با استفاده از Hash Function به اطلاعاتی تبدیل می‌شود که پیدا کردن مقدار مرتبط با آن را سریع‌تر می‌کند.

## Complexity

در یک Hash Table مناسب، جستجو در حالت میانگین معمولاً:

```text
O(1)
```

در نظر گرفته می‌شود.

Insert و Delete نیز در حالت میانگین معمولاً بسیار سریع هستند.

البته `O(1)` به این معنی نیست که تمام عملیات در هر شرایطی دقیقاً به یک مقدار زمان نیاز دارند.

جزئیات پیاده‌سازی و شرایط خاص نیز وجود دارند.

## Collision

گاهی دو Key متفاوت ممکن است به یک محل داخلی یکسان برسند.

به این اتفاق **Collision** گفته می‌شود.

Hash Tableها روش‌هایی برای مدیریت Collision دارند.

فعلاً همین که بدانم Collision چیست کافی است.

## کاربردها

Hash Tableها تقریباً همه‌جا استفاده می‌شوند:

* Dictionaries
* Caches
* Configuration
* Frequency counting
* Lookup tables
* User data
* Indexes
* Sets

## مدل ذهنی

Hash Table را این‌گونه تصور می‌کنم:

> یک سیستم ذخیره‌سازی برچسب‌دار.

به‌جای اینکه شماره‌ی موقعیت را بدانم، از یک Key معنادار استفاده می‌کنم.

## نکته‌ی اصلی

Hash Table داده را به شکل:

```text
key → value
```

ذخیره می‌کند و برای جستجوی سریع بر اساس Key طراحی شده است.

# 7. Tree

**Tree** یک ساختمان داده‌ی سلسله‌مراتبی است.

برخلاف یک دنباله‌ی ساده، عناصر می‌توانند رابطه‌ی Parent و Child داشته باشند.

مثلاً:

```text
        A
       / \
      B   C
     / \
    D   E
```

## اصطلاحات مهم

### Root

بالاترین Node در Tree.

در مثال بالا:

```text
A
```

Root است.

### Parent

Nodeای که Nodeهای دیگری زیر آن قرار دارند.

مثلاً:

```text
B
```

Parent مربوط به `D` و `E` است.

### Child

Nodeای که مستقیماً زیر یک Node دیگر قرار دارد.

`D` و `E` فرزندان `B` هستند.

### Leaf

Nodeای که Child ندارد.

در مثال:

```text
D
E
C
```

Leaf هستند.

## مثال واقعی

ساختار پوشه‌ها را می‌توان شبیه Tree در نظر گرفت:

```text
Projects
├── backend
│   ├── api
│   └── database
│
└── frontend
    ├── components
    └── pages
```

بسیاری از سیستم‌های سلسله‌مراتبی را می‌توان با Tree مدل کرد.

## Binary Tree

در **Binary Tree** هر Node حداکثر دو Child دارد.

مثلاً:

```text
        10
       /  \
      5    20
```

فعلاً فقط لازم است این مفهوم را بشناسم.

## Binary Search Tree

در **Binary Search Tree (BST)** علاوه بر ساختار درختی، یک قانون مرتب‌سازی نیز وجود دارد.

به شکل ساده:

```text
smaller values ← node → larger values
```

مثلاً:

```text
        10
       /  \
      5    20
     / \
    2   7
```

بعداً Treeها و BST را به شکل عمیق‌تر مطالعه خواهم کرد.

## مدل ذهنی

Tree را این‌طور تصور می‌کنم:

> یک ساختار سلسله‌مراتبی که از بالا شروع می‌شود و به شاخه‌های مختلف تقسیم می‌شود.

## نکته‌ی اصلی

فعلاً باید این مفاهیم را بفهمم:

* Node
* Root
* Parent
* Child
* Leaf
* Hierarchy

---

# 8. Graph

**Graph** برای نمایش ارتباط میان اشیا استفاده می‌شود.

Graph عمدتاً از دو بخش تشکیل شده است:

```text
Vertices / Nodes
Edges
```

مثلاً:

```text
A ----- B
|       |
|       |
C ----- D
```

`A`، `B`، `C` و `D`، Node یا Vertex هستند.

خطوط میان آن‌ها Edge هستند.

## چرا Graph مهم است؟

بسیاری از مسائل دنیای واقعی به‌صورت طبیعی با Graph مدل می‌شوند.

مثلاً:

* شبکه‌ی جاده‌ها
* شبکه‌های اجتماعی
* شبکه‌های کامپیوتری
* مسیرهای پرواز
* سیستم‌های پیشنهاددهی
* Dependencies
* لینک‌های صفحات وب

## مثال شبکه‌ی اجتماعی

فرض کنیم:

```text
Sina ----- Ali
  |
  |
 Reza ---- Sara
```

آدم‌ها Node هستند.

ارتباط میان آن‌ها Edge است.

## Undirected Graph

در یک Graph بدون جهت، ارتباط جهت خاصی ندارد.

```text
A ----- B
```

یعنی:

```text
A is connected to B
B is connected to A
```

## Directed Graph

در Graph جهت‌دار از فلش استفاده می‌شود:

```text
A → B
```

این رابطه الزاماً به معنای زیر نیست:

```text
B → A
```

مثلاً در یک شبکه اجتماعی ممکن است A، B را Follow کند ولی B، A را Follow نکند.

## Weighted Graph

در بعضی Graphها، Edgeها مقدار یا وزن دارند.

مثلاً:

```text
Berlin ---- 190 km ---- Leipzig
```

وزن می‌تواند نشان‌دهنده‌ی موارد زیر باشد:

* Distance
* Time
* Cost
* Risk
* Capacity

Weighted Graphها بعداً برای الگوریتم‌هایی مثل Shortest Path اهمیت زیادی پیدا می‌کنند.

## Graph Algorithms

بعداً الگوریتم‌هایی مانند این‌ها را مطالعه خواهم کرد:

```text
Breadth-First Search (BFS)
Depth-First Search (DFS)
Dijkstra's Algorithm
```

این الگوریتم‌ها به سؤال‌هایی مانند این پاسخ می‌دهند:

* آیا می‌توان از یک Node به Node دیگری رسید؟
* چه Nodeهایی به یکدیگر متصل‌اند؟
* کوتاه‌ترین مسیر چیست؟
* ابتدا باید کدام Nodeها بررسی شوند؟

## مدل ذهنی

Graph را این‌گونه تصور می‌کنم:

> مجموعه‌ای از چیزها به همراه ارتباط میان آن‌ها.

## نکته‌ی اصلی

Graph یعنی:

```text
nodes + connections
```

و برای مدل‌سازی شبکه‌ها و روابط بسیار مناسب است.

# 9. عملیات رایج روی ساختمان داده‌ها

ساختمان داده‌های مختلف، عملیات مختلف را با سرعت‌های متفاوت انجام می‌دهند.

این اصطلاحات هنگام مطالعه‌ی الگوریتم‌ها بسیار تکرار می‌شوند.

## Access

دسترسی به یک عنصر وقتی موقعیت یا Key آن را می‌دانیم.

مثلاً:

```python
numbers[3]
```

## Search

پیدا کردن یک مقدار وقتی محل آن را نمی‌دانیم.

مثلاً:

```text
Find 42 inside a collection.
```

## Insert

اضافه کردن یک عنصر جدید.

مثلاً:

```text
Before:

[10, 20, 30]

After inserting 15:

[10, 15, 20, 30]
```

## Delete

حذف یک عنصر.

مثلاً:

```text
Before:

[10, 20, 30]

Delete 20:

[10, 30]
```

## Traverse

حرکت روی عناصر یکی پس از دیگری.

مثلاً:

```text
A → B → C → D
```

Traversal به‌خصوص در این ساختارها اهمیت دارد:

* Linked Lists
* Trees
* Graphs

## چرا این عملیات مهم هستند؟

هنگام انتخاب ساختمان داده نباید فقط بپرسم:

> آیا می‌توانم اطلاعاتم را در این ساختار ذخیره کنم؟

بلکه باید بپرسم:

> برنامه‌ی من بیشتر چه عملیاتی روی این داده‌ها انجام خواهد داد؟

ممکن است یک ساختمان داده در Search بسیار سریع باشد ولی برای عملیات دیگری مناسب نباشد.

معمولاً بین مزایا و معایب مختلف یک **Trade-off** وجود دارد.

# 10. مقدمات Big O

برای مقایسه‌ی الگوریتم‌ها و ساختمان داده‌ها باید بتوانم توضیح بدهم با بزرگ‌تر شدن ورودی، مقدار کار چقدر افزایش پیدا می‌کند.

اینجاست که **Big O notation** اهمیت پیدا می‌کند.

Big O اساساً برای اندازه‌گیری دقیق زمان اجرا برحسب ثانیه نیست.

بلکه نشان می‌دهد با بزرگ شدن ورودی، مقدار کار مورد نیاز الگوریتم چگونه رشد می‌کند.

فرض کنیم:

```text
n = number of items
```

---

## O(1) — Constant Time

مثلاً:

```python
numbers[5]
```

اگر index را بدانم، برای رسیدن به آن لازم نیست عناصر قبل از آن را یکی‌یکی بررسی کنم.

به‌صورت مفهومی:

```text
10 items        → roughly constant work
1,000 items     → roughly constant work
1,000,000 items → roughly constant work
```

این را:

```text
O(1)
```

می‌نامیم.

### مدل ذهنی

> دقیقاً می‌دانم باید کجا بروم.

---

## O(log n) — Logarithmic Time

یکی از معروف‌ترین مثال‌ها:

```text
Binary Search
```

است.

Binary Search به‌جای بررسی تمام عناصر، در هر مرحله تقریباً نصف گزینه‌های باقی‌مانده را حذف می‌کند.

فرض کنیم حدود یک میلیون مقدار مرتب داشته باشیم.

یک روش خطی ممکن است تعداد بسیار زیادی از عناصر را بررسی کند.

اما Binary Search برای چنین داده‌ای تقریباً به حدود:

```text
20 comparisons
```

نیاز دارد.

این تفاوت بسیار مهم است.

### مدل ذهنی

> در هر مرحله بخش بزرگی از مسئله را حذف می‌کنم.

---

## O(n) — Linear Time

فرض کنیم یک List را عنصر به عنصر بررسی کنیم:

```python
for number in numbers:
    if number == target:
        break
```

با بیشتر شدن تعداد عناصر، مقدار کار نیز تقریباً به همان نسبت افزایش پیدا می‌کند.

```text
10 items      → up to about 10 checks
100 items     → up to about 100 checks
1,000 items   → up to about 1,000 checks
```

این می‌شود:

```text
O(n)
```

### مدل ذهنی

> ممکن است مجبور باشم تمام عناصر را یک بار بررسی کنم.

---

## O(n log n)

این Complexity را در تعدادی از الگوریتم‌های مرتب‌سازی کارآمد می‌بینیم.

مثلاً:

```text
Merge Sort
Heap Sort
Quicksort — average case
```

فعلاً لازم نیست جزئیات ریاضی آن را بدانم.

فقط باید بدانم:

```text
O(n log n)
```

برای داده‌های بزرگ معمولاً بسیار بهتر از:

```text
O(n²)
```

مقیاس‌پذیر است.

---

## O(n²) — Quadratic Time

یک نمونه‌ی رایج، Loop تو در تو است:

```python
for x in numbers:
    for y in numbers:
        pass
```

اگر `n` عنصر داشته باشیم، کار داخلی ممکن است تقریباً `n × n` بار انجام شود.

مثلاً:

```text
100 items

100 × 100
= 10,000 operations
```

و برای:

```text
1,000 items
```

ممکن است تقریباً:

```text
1,000,000 operations
```

داشته باشیم.

بنابراین با بزرگ شدن ورودی، هزینه به‌سرعت افزایش پیدا می‌کند.

### مدل ذهنی

> برای هر عنصر، ممکن است مجبور باشم دوباره تمام عناصر را بررسی کنم.

---

# 11. مقایسه‌ی نرخ رشد

به شکل ساده، از مقیاس‌پذیری بهتر به بدتر:

```text
O(1)
 ↓
O(log n)
 ↓
O(n)
 ↓
O(n log n)
 ↓
O(n²)
```

وقتی تعداد داده‌ها بسیار زیاد شود، تفاوت میان این Complexityها اهمیت زیادی پیدا می‌کند.

ممکن است یک الگوریتم برای 100 عنصر کاملاً مناسب باشد، اما برای 100 میلیون عنصر بسیار کند شود.

بنابراین فقط نباید بپرسم:

> آیا کد من کار می‌کند؟

بلکه باید بپرسم:

> اگر ورودی خیلی بزرگ‌تر شود، راه‌حل من چگونه رفتار خواهد کرد؟

# 12. مقایسه‌ی سریع ساختمان داده‌ها

این جدول فقط یک دید کلی و ساده ارائه می‌دهد. Complexity دقیق می‌تواند به نوع پیاده‌سازی بستگی داشته باشد.

| ساختار       | ایده‌ی اصلی         | نقطه‌ی قوت معمول          |
| ------------ | ------------------- | ------------------------- |
| Array / List | دنباله‌ی مرتب       | دسترسی سریع با index      |
| Linked List  | Nodeهای متصل        | Insert/Delete انعطاف‌پذیر |
| Stack        | LIFO                | پردازش جدیدترین عنصر      |
| Queue        | FIFO                | پردازش بر اساس ترتیب ورود |
| Hash Table   | Key-Value           | جستجوی سریع با Key        |
| Tree         | ساختار سلسله‌مراتبی | نمایش Hierarchy           |
| Graph        | Node و Relationship | نمایش شبکه‌ها و ارتباط‌ها |

# 13. مدل‌های ذهنی

این مدل‌های ساده کمک می‌کنند ساختمان داده‌ها را راحت‌تر به خاطر بسپارم.

### Array

```text
یک ردیف جعبه‌ی شماره‌گذاری‌شده.
```

### Linked List

```text
یک زنجیر که هر Node مسیر Node بعدی را می‌داند.
```

### Stack

```text
یک دسته بشقاب.

آخرین چیزی که اضافه شده، اولین چیزی است که برداشته می‌شود.
```

### Queue

```text
یک صف از آدم‌ها.

کسی که زودتر آمده، زودتر سرویس می‌گیرد.
```

### Hash Table

```text
یک سیستم ذخیره‌سازی با برچسب.

Key → Value
```

### Tree

```text
یک ساختار سلسله‌مراتبی که به شاخه‌های مختلف تقسیم می‌شود.
```

### Graph

```text
اشیا به همراه ارتباط میان آن‌ها.
```

# 14. قبل از شروع جدی الگوریتم‌ها چه چیزهایی باید یادم باشد؟

در این مرحله لازم نیست بتوانم تمام ساختمان داده‌ها را بدون کمک از صفر پیاده‌سازی کنم.

فعلاً باید مفاهیم اصلی را به خاطر داشته باشم.

### Arrays / Lists

* مجموعه‌ی مرتب
* Index
* دسترسی سریع با Index
* Search ممکن است نیاز به Traversal داشته باشد

### Linked Lists

* از Node ساخته می‌شوند
* Nodeها به یکدیگر اشاره می‌کنند
* دسترسی مستقیم معمولی با Index ندارند
* برای رسیدن به عناصر باید لینک‌ها را دنبال کنیم

### Stacks

```text
LIFO
```

### Queues

```text
FIFO
```

### Hash Tables

```text
key → value
```

Lookup در حالت میانگین معمولاً بسیار سریع است.

### Trees

باید این مفاهیم را بشناسم:

```text
root
parent
child
leaf
```

### Graphs

باید این مفاهیم را بشناسم:

```text
vertex / node
edge
directed
undirected
weighted
```

### Big O

باید این Complexityها را تشخیص بدهم:

```text
O(1)
O(log n)
O(n)
O(n log n)
O(n²)
```

# 15. جمع‌بندی

مهم‌ترین چیزی که از این بخش باید یاد بگیرم این است که هیچ ساختمان داده‌ای وجود ندارد که برای همه‌ی مسائل بهترین انتخاب باشد.

هر ساختمان داده بعضی عملیات را ساده‌تر یا سریع‌تر می‌کند و در مقابل محدودیت‌ها یا هزینه‌های خودش را دارد.

قبل از انتخاب یک ساختمان داده باید از خودم بپرسم:

```text
چه نوع داده‌ای را ذخیره می‌کنم؟

چگونه به این داده‌ها دسترسی خواهم داشت؟

آیا زیاد Search انجام می‌دهم؟

آیا Insert و Delete زیاد دارم؟

آیا ترتیب داده‌ها مهم است؟

آیا میان داده‌ها Relationship وجود دارد؟

حجم داده ممکن است تا چه اندازه بزرگ شود؟
```

درک این سؤال‌ها کمک می‌کند بعدها بفهمم چرا الگوریتم‌های مختلف از ساختمان داده‌های متفاوت استفاده می‌کنند.

قدم بعدی من این است که الگوریتم‌ها را عمیق‌تر مطالعه کنم و به‌مرور این مفاهیم را به پیاده‌سازی‌های واقعی، Test، Visualization و Benchmark تبدیل کنم.
